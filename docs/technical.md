# 技术说明

## 设计目的
GPIPA 的目标不是构建一个通用的端到端语音大模型，而是为“汉语语音边界检测与 IPA 转写”这一类任务提供一条足够稳定、可解释、可调试的工程路径。项目的设计中心始终不是单点精度的追逐，而是让声学边界、文本转写和 IPA 表达之间形成一条结构清晰的处理链，使最终输出能够自然落到 Praat / TextGrid 这样的语言学分析工具中。

## 结构
从整体结构上看，GPIPA 把问题拆成了三个性质不同但彼此耦合紧密的子任务。第一部分是语音到汉字的识别，这一部分解决“说了什么”的问题。第二部分是汉字到拼音、再到 IPA 的符号转换，这一部分解决“应当对齐到什么符号序列”的问题。第三部分是基于声学模型输出和目标音系序列的强制对齐，它解决“这些符号在时间轴上各自落在哪里”的问题。项目之所以采用这样的拆分，是因为边界检测本身并不等价于转写，而转写正确也不自动意味着边界合理。只有把“文本内容”和“时间结构”分开处理，再在后端显式会合，才能得到既能读、又能检验、还能修正的结果。

### ASR 模块
在 ASR 层，项目当前使用 `Qwen3-ASR-0.6B` 作为参考识别模型，对应实现位于 gpipa/asr/qwen_asr.py。这一层的职责被有意保持得很窄：它只负责把输入音频转成汉字文本，并把模型加载逻辑封装在一个独立模块中。较新的实现已经改为懒加载，这意味着模型不会在包导入阶段立即初始化，而是在真正需要识别时才加载。这样做的直接收益是，UI、推理流程和环境检测不会因为 GPU 配置或 CUDA 版本不匹配而在导入阶段提前失败。模型路径、设备映射和 dtype 都通过环境变量控制，因此这一层虽然依赖较重，但在工程边界上是清晰的。

### G2P 模块
文本进入系统之后，会先经过 G2P 模块。相关实现主要位于 gpipa/g2p/g2p_utils.py。这一层的关键价值不在于“把汉字转成拼音”本身，因为这一步已有成熟工具可做，而在于把结果规范化到声学对齐真正可用的词表形式。普通拼音序列并不能直接送入对齐器，原因是训练语料、音节划分方式和 IPA 映射规则之间存在项目内部约定。

例如，代码会把 `zi/ci/si` 这一类舌尖元音形式归一化为 `zii/cii/sii`，把 `zhi/chi/shi` 归一化为 `zhiii/chiii/shiii`，以匹配训练阶段实际使用的标签体系。除此之外，模块还显式实现了“一”“不”的变调和连续上声变调，并通过词表文件处理儿化现象。这些步骤并不华丽，但它们决定了后续强制对齐是否建立在一个正确、稳定、可重复的音系表示之上。

### 声学和对齐模块
声学层的核心是一个轻量的逐帧分类模型，定义在 gpipa/acoustic/model.py，训练入口位于 gpipa/acoustic/train.py。从训练逻辑可以看出，项目采用的是非常明确的监督式设定：从标注语料中读取音频和区间标注，将每帧映射到目标标签，再训练 BiLSTM 做逐帧分类。输入特征使用 `torchaudio.compliance.kaldi.fbank` 生成的 80 维 fbank，标签侧则来自 TextGrid / interval 标注解析后得到的音节或音素序列。训练过程中会构建 `label2id` 映射，并把它与模型参数一起写入 checkpoint；同时还会把词表单独保存为 `vocab.json`。这一设计很重要，因为它让推理阶段不必重新扫描训练集来恢复标签空间，而可以直接从 checkpoint 和词表中得到完整的标签定义。

边界检测并不是简单地取逐帧 argmax。GPIPA 的关键技术点在于，它把声学模型输出与显式目标序列结合起来，通过 Viterbi 风格的强制对齐获得更可信的边界结果。相关实现在 gpipa/acoustic/alignment.。这里的对齐并非标准 CTC 解码的直接复用，而是在 CTC 状态路径的基础上加入了更适合本任务的停留代价、blank 停留代价、软长度约束和超时惩罚。换句话说，模型输出提供“某一帧更像哪个标签”的局部证据，Viterbi 过程则把这些局部证据组织成一条整体上更合理的时间路径。对于边界检测任务来说，这种“局部概率 + 全局约束”的组合通常比完全独立的逐帧决策更稳，因为它天然抑制了过度抖动，也能更好地尊重目标音节序列的顺序结构。

### 预处理：VAD 和静音分段
项目在推理路径中还引入了静音处理策略。对较长音频，系统会先调用 Silero VAD 做切分，再把每个片段分别送入 ASR、G2P 和对齐流程，最后合并为一个总的 TextGrid。相关逻辑位于 gpipa/pipeline.py。这里体现的是一种非常工程化的权衡：长音频如果直接整体处理，不仅 ASR 和对齐的稳定性会下降，错误也更难诊断；而切段处理可以限制错误传播范围，并允许在 UI 中逐段展示结果。为了避免切得过碎，代码还对 VAD 片段做了合并、最小时长过滤和最大长度重切分。最后输出阶段再把各段 TextGrid 在时间轴上平移回原始位置，从而重建完整语音的分层标注结果。

### TextGrid 生成
TextGrid 生成时，系统并不只输出一个底层 phones tier，而是重写为 Sentence、Word 和 Phoneme 三层结构。Sentence 层保留 ASR 的整句文本，Word 层根据分词结果和音节数量对时间进行近似分配，Phoneme 层则保存真正用于分析的对齐结果。这样的输出组织方式表明，GPIPA 的目标不仅是“跑出一个边界”，而是为后续人工校对、语言学分析和教学展示提供一个可直接使用的中间成果。技术上，这意味着项目需要同时顾及文本可读性和时间对齐精度，而不是只优化其中一端。

### UI 模块
UI 层由 Gradio 实现，位于 gpipa/ui/app.py。它并不承载核心算法，而是把配置编辑、音频上传、分段结果展示和 TextGrid 文件导出统一到一个调试界面中。这个界面的价值在于把原本分散在命令行、配置文件和中间产物中的状态集中展示出来，使问题定位从“黑箱式运行”转变为“逐阶段检查”。从工程实践上说，这对于语音处理项目非常重要，因为实际故障往往并不发生在模型本身，而是发生在依赖环境、配置路径、音频格式、词表一致性或外部模型加载上。

## 为什么不使用 Wav2Vec2.0 等现代大型模型？
在实验过程中，我们确实尝试过将类似 Wav2Vec 2.0 的自监督语音模型直接用于边界检测与对齐任务。然而，这类模型在本项目设定下暴露出一个结构性问题：它们的表示能力，并不是为“精细时间边界”服务的。

从训练目标上看，Wav2Vec2.0 及其后续模型优化的是“语音内容的判别性表示”，而不是“时间结构的可分辨性”。其核心任务是通过对比学习或掩码预测，使模型能够在较长时间上下文中恢复被遮蔽的语音片段。这一过程会鼓励模型逐渐忽略短时间尺度上的细粒度差异，而强化跨帧、跨音素的上下文一致性表示。

[这篇论文](https://arxiv.org/abs/2107.04734)实际上告诉我们，已有明确观察：随着模型层数加深，隐藏表示的时间分辨率显著下降，模型对具体帧级边界的敏感性逐渐被语义级信息所取代。换句话说，模型“越来越知道你在说什么”，但“越来越不关心你是在哪一毫秒开始说的”。

对于自动语音识别（ASR）任务，这种特性是优势，因为最终目标是获得稳定的文本输出；但对于本项目的核心任务——音节或音素级别的边界检测——这反而成为一种系统性偏差。边界检测本质上依赖于局部声学特征的突变，例如共振峰结构的快速变化、能量分布的转移或清浊音的切换，而这些信息恰恰是大模型在高层表示中主动压缩甚至抹平的部分。

进一步地，从解码机制上看，这类模型通常通过 CTC 或 seq2seq 结构输出文本，其时间对齐信息是隐式的，甚至是不可恢复的。虽然可以通过 CTC alignment 或 attention 可视化来“近似”恢复时间信息，但这些方法本质上是对模型内部结构的事后解释，而非模型训练目标的一部分。因此，它们在边界稳定性、可重复性和可解释性上都存在明显不足。

相比之下，GPIPA 所采用的方案刻意保持了声学层的“低级性”。基于 fbank 的逐帧特征与 BiLSTM 分类模型，并不会主动压缩时间分辨率，而是直接对每一帧做出标签判断。这种设计在“语义表达能力”上显然不如大模型，但它保留了边界检测所必需的局部敏感性。

更重要的是，通过将声学模型输出与显式的音系目标序列结合，并在后端引入 Viterbi 风格的强制对齐，系统把“时间结构”从模型内部隐变量转化为一个可以显式建模、调参和调试的过程。这种分层设计使得边界的形成机制是可追踪的：可以明确区分是声学证据不足，还是路径约束设置不合理，从而为系统性改进提供依据。
